================================================================================
     GUIA COMPLETA: COMO CORRER SIIF2 CON DOCKER EN WINDOWS 11
     (Paso a paso - MySQL + DBeaver + Laravel)
================================================================================

Estimado usuario, esta guia le explicara paso a paso como:

  1. Instalar Docker en Windows 11
  2. Descargar y correr el proyecto SIIF2
  3. Migrar/cargar la base de datos en MySQL
  4. Instalar DBeaver y conectarse a la base de datos
  5. Ejecutar comandos de Laravel (php artisan migrate, etc.)

Tome su tiempo, siga cada paso en orden, y no se salte ninguno.


================================================================================
PARTE 1: INSTALAR DOCKER DESKTOP EN WINDOWS 11
================================================================================

Docker es un programa que crea "contenedores" (como pequenas computadoras
virtuales) donde correra nuestro proyecto. No necesita instalar PHP, MySQL
ni nada mas por separado. Docker se encarga de todo.

PASO 1.1 - Descargar Docker Desktop
----------------------------------------------------------------------
  a) Abra su navegador (Chrome, Edge, etc.)
  b) Vaya a esta direccion: https://www.docker.com/products/docker-desktop/
  c) Haga clic en el boton azul "Download for Windows"
  d) Se descargara un archivo llamado "Docker Desktop Installer.exe"
  e) Espere a que termine la descarga

PASO 1.2 - Instalar Docker Desktop
----------------------------------------------------------------------
  a) Vaya a su carpeta de Descargas
  b) Haga doble clic en "Docker Desktop Installer.exe"
  c) Si Windows le pregunta "Desea permitir que esta aplicacion haga
     cambios en su dispositivo?", haga clic en "Si"
  d) En la ventana de instalacion:
     - Asegurese de que la casilla "Use WSL 2 instead of Hyper-V"
       este MARCADA (con una palomita/check)
     - Haga clic en "Ok"
  e) Espere a que termine la instalacion (puede tardar 5-10 minutos)
  f) Cuando termine, haga clic en "Close and restart"
     (Esto REINICIARA su computadora)

PASO 1.3 - Configurar Docker Desktop despues del reinicio
----------------------------------------------------------------------
  a) Despues de reiniciar, Docker Desktop se abrira automaticamente
     (Si no se abre, busquelo en el menu Inicio: "Docker Desktop")
  b) Le pedira aceptar los terminos de servicio. Haga clic en "Accept"
  c) Puede saltarse el registro (Skip / Continue without signing in)
  d) Espere a que Docker termine de iniciarse
     - Vera un icono de una ballena en la barra de tareas (abajo a
       la derecha, cerca del reloj)
     - Cuando la ballena deje de moverse, Docker esta listo
  e) Para verificar que funciona:
     - Abra "PowerShell" (busquelo en el menu Inicio)
     - Escriba este comando y presione Enter:

         docker --version

     - Deberia ver algo como: "Docker version 27.x.x"
     - Si ve eso, Docker esta instalado correctamente

PARTE 2: DESCARGAR EL PROYECTO SIIF2
================================================================================

PASO 2.1 - Instalar Git (si no lo tiene)
----------------------------------------------------------------------
  a) Vaya a: https://git-scm.com/downloads/win
  b) Descargue el instalador para Windows (64-bit)
  c) Ejecute el instalador

PASO 2.2 - Descargar el proyecto
----------------------------------------------------------------------
  a) Abra PowerShell (busquelo en el menu Inicio)
  b) Navegue a donde quiere guardar el proyecto. Por ejemplo,
     para guardarlo en el Escritorio, escriba:

         cd ~/Desktop

  c) Descargue el proyecto con este comando:

         git clone https://github.com/ADmosnt/Siif2.git

         cd Siif2


================================================================================
PARTE 3: CONFIGURAR EL ARCHIVO .env
================================================================================

El archivo .env es como la "tarjeta de configuracion" del proyecto.
Le dice al programa donde esta la base de datos, que contrasenas usar, etc.

PASO 3.1 - Crear el archivo .env
----------------------------------------------------------------------
  a) Dentro de la carpeta Siif2 en PowerShell, ejecute:

         copy .env.example_with_docker_mysql .env

     Esto crea una copia del archivo de ejemplo con el nombre correcto.

PASO 3.2 - (OPCIONAL) Verificar el contenido
----------------------------------------------------------------------
  Si desea ver o editar el archivo, puede abrirlo con el Bloc de Notas:

         notepad .env

  Los valores importantes que ya vienen configurados son:

      DB_CONNECTION=mysql
      DB_HOST=db
      DB_PORT=3306
      DB_DATABASE=appserviciosinte_siif
      DB_USERNAME=laravel_user
      DB_PASSWORD=0690164
      APP_URL=http://localhost:8080

  IMPORTANTE: No cambie DB_HOST=db  (ese "db" es el nombre interno
  que Docker usa para comunicarse con la base de datos)


================================================================================
PARTE 4: LEVANTAR EL PROYECTO CON DOCKER
================================================================================

Ahora viene la parte mas importante: encender todo el sistema.
Docker va a crear 4 "contenedores" (maquinas virtuales pequenas):

  - "app"    = El servidor PHP/Laravel (el cerebro del sistema)
  - "node"   = El compilador de Vue/JavaScript (la cara del sistema)
  - "nginx"  = El servidor web (el que recibe las visitas)
  - "db"     = La base de datos MySQL (donde se guardan los datos)

PASO 4.1 - Construir y levantar los contenedores
----------------------------------------------------------------------
  a) Asegurese de que Docker Desktop este corriendo (la ballena
     en la barra de tareas debe estar quieta, no moviendose)

  b) En PowerShell, dentro de la carpeta Siif2, ejecute:

         docker compose up --build -d

     Explicacion del comando:
       docker compose up  = "enciende todo el sistema"
       --build            = "construye las imagenes desde cero"
       -d                 = "en segundo plano" (para que no ocupe
                            la ventana de PowerShell)

  c) LA PRIMERA VEZ tardara entre 5 y 15 minutos porque tiene que:
     - Descargar PHP, Node.js, Nginx y MySQL de internet
     - Instalar todas las librerias del proyecto
     - Crear la base de datos

     Vera muchas lineas de texto pasando en la pantalla.
     Esto es NORMAL. Espere pacientemente.

  d) Cuando termine, vera algo como:
       [+] Running 4/4
        - Container laravel-db     Started
        - Container vue-build      Started
        - Container siif2-app-1    Started
        - Container laravel-nginx  Started

PASO 4.2 - Verificar que todo esta corriendo
----------------------------------------------------------------------
  Ejecute este comando para ver el estado de los contenedores:

         docker compose ps

  Deberia ver 4 contenedores con el estado "Up" o "running":

      NAME              STATUS
      laravel-db        Up (healthy)
      vue-build         Up
      siif2-app-1       Up
      laravel-nginx     Up

  Si algun contenedor dice "Restarting" o "Exit", espere 30 segundos
  y ejecute el comando otra vez. A veces la base de datos tarda un
  poco en estar lista.

PASO 4.3 - Ver los logs (si algo no funciona)
----------------------------------------------------------------------
  Si necesita ver que esta pasando dentro de los contenedores:

  - Ver TODO lo que pasa:

         docker compose logs

  - Ver solo lo de la base de datos:

         docker compose logs db

  - Ver solo lo del servidor PHP:

         docker compose logs app

  - Ver los logs EN VIVO (se actualizan en tiempo real):

         docker compose logs -f

    (Para dejar de ver los logs en vivo, presione Ctrl + C)

PASO 4.4 - Abrir el sistema en el navegador
----------------------------------------------------------------------
  a) Abra su navegador (Chrome, Edge, etc.)
  b) Escriba en la barra de direcciones:

         http://localhost:8080

  c) Deberia ver la pagina de inicio de sesion de SIIF2

  NOTA: Si ve una pagina en blanco o un error, espere 1-2 minutos
  mas y recargue la pagina (F5). El servidor de Vue (Vite) puede
  tardar un poco en compilar todo la primera vez.


================================================================================
PARTE 5: LA BASE DE DATOS - COMO FUNCIONA
================================================================================

El proyecto ya incluye un archivo SQL que carga automaticamente los datos
iniciales cuando Docker crea la base de datos por primera vez.

Este archivo esta en:
    Siif2/docker-entrypoint-initdb.d/01_dump_patched.sql

Docker/MySQL lo ejecuta AUTOMATICAMENTE la primera vez que se crea
el contenedor de base de datos. Usted NO necesita hacer nada extra.

PASO 5.1 - Ejecutar migraciones de Laravel (IMPORTANTE)
----------------------------------------------------------------------
  Las migraciones son archivos que crean o modifican las tablas de la
  base de datos. Se ejecutan con "php artisan migrate".

  Como el PHP esta DENTRO de Docker (no en su computadora), el comando
  se ejecuta asi:

         docker compose exec app php artisan migrate --force

  Explicacion:
    docker compose exec app  = "ejecuta un comando dentro del
                                contenedor llamado 'app'"
    php artisan migrate      = "crea/actualiza las tablas"
    --force                  = "hacerlo sin preguntar confirmacion"

  NOTA: El script de inicio (init.sh) ya ejecuta las migraciones
  automaticamente al encender el contenedor. Solo necesita este
  comando si agrega nuevas migraciones despues.

PASO 5.2 - Otros comandos utiles de Laravel con Docker
----------------------------------------------------------------------

  * Limpiar toda la cache:

         docker compose exec app php artisan optimize:clear

  * Ver las rutas del sistema:

         docker compose exec app php artisan route:list

  * Crear un nuevo archivo de migracion:

         docker compose exec app php artisan make:migration nombre_de_la_migracion

  * Deshacer la ultima migracion:

         docker compose exec app php artisan migrate:rollback

  * Rehacer TODAS las migraciones (CUIDADO: borra todos los datos):

         docker compose exec app php artisan migrate:fresh

  * Entrar al contenedor PHP directamente (como si fuera otra
    computadora, para ejecutar multiples comandos):

         docker compose exec app bash

    Una vez dentro, puede ejecutar comandos directamente:
         php artisan migrate
         php artisan tinker
         composer install

    Para salir del contenedor, escriba:
         exit


================================================================================
PARTE 6: INSTALAR DBEAVER Y CONECTARSE A MYSQL
================================================================================

DBeaver es un programa gratuito para ver y manejar bases de datos.
Es como un "Excel para bases de datos": le permite ver las tablas,
los datos, ejecutar consultas SQL, etc.

PASO 6.1 - Descargar DBeaver
----------------------------------------------------------------------
  a) Vaya a: https://dbeaver.io/download/
  b) En la seccion "Community Edition" (la version gratuita),
     haga clic en "Windows (installer)"
  c) Descargue el archivo .exe

PASO 6.2 - Instalar DBeaver
----------------------------------------------------------------------
  a) Ejecute el archivo descargado
  b) Si Windows pregunta por permisos, haga clic en "Si"
  c) Siga el instalador:
     - Idioma: Espanol (o el que prefiera)
     - Aceptar la licencia
     - Dejar las opciones por defecto
     - Haga clic en "Siguiente" en cada pantalla
     - Al final, haga clic en "Instalar"
  d) Cuando termine, haga clic en "Finalizar"

PASO 6.3 - Crear la conexion a MySQL
----------------------------------------------------------------------
  a) Abra DBeaver (busquelo en el menu Inicio)

  b) Haga clic en el icono del enchufe con el signo "+" en la
     esquina superior izquierda (tooltip: "Nueva conexion")
     O bien vaya al menu: Base de datos > Nueva conexion

  c) En la ventana que aparece, busque y seleccione "MySQL"
     (tiene un icono de un delfin azul)
     Haga clic en "Siguiente"

  d) En la pantalla de configuracion, llene estos datos EXACTAMENTE:

     +--------------------------+------------------------------+
     | Campo                    | Valor                        |
     +--------------------------+------------------------------+
     | Server Host              | localhost                    |
     | Port                     | 3309                         |
     | Database                 | appserviciosinte_siif        |
     | Username                 | laravel_user                 |
     | Password                 | 0690164                      |
     +--------------------------+------------------------------+

     ATENCION CON EL PUERTO: es 3309, NO 3306
     (Docker redirige el puerto 3306 interno al 3309 externo
      para no chocar con algun MySQL que tenga instalado)

  e) Haga clic en "Test Connection..." (boton en la esquina inferior
     izquierda de la ventana)

     - Si es la primera vez, DBeaver le pedira descargar el "driver"
       de MySQL. Haga clic en "Download" o "Descargar". Esto es
       normal y solo pasa una vez.

     - Si todo esta bien, vera un mensaje verde:
       "Connected" o "Conexion exitosa"

     - Si ve un error:
       * Verifique que Docker este corriendo (la ballena en la
         barra de tareas)
       * Verifique que los contenedores esten encendidos:
         Abra PowerShell y ejecute: docker compose ps
       * Verifique que escribio el puerto 3309 (no 3306)
       * Verifique que la contrasena sea correcta: 0690164

  f) Haga clic en "Finalizar" para guardar la conexion

PASO 6.4 - Explorar la base de datos
----------------------------------------------------------------------
  a) En el panel izquierdo de DBeaver, vera la nueva conexion
  b) Haga doble clic en ella para conectarse
  c) Se desplegaran las carpetas:
     - appserviciosinte_siif
       - Tablas
         - cache
         - failed_jobs
         - migrations
         - sessions
         - t_actividades
         - t_bitacoras
         - t_ciclos
         - t_ciudades
         - t_clases
         - ... (muchas mas tablas)

  d) Para ver los datos de una tabla:
     - Haga doble clic en el nombre de la tabla (ej: "t_personas")
     - Se abrira una pestana con los datos en formato de tabla
     - Puede hacer scroll para ver todos los registros

  e) Para ejecutar una consulta SQL:
     - Haga clic derecho en la conexion > "SQL Editor" > "Nuevo script SQL"
     - Escriba su consulta, por ejemplo:

         SELECT * FROM t_personas LIMIT 10;

     - Presione Ctrl + Enter para ejecutarla
     - Los resultados apareceran abajo

PARTE 7: MIGRAR DATOS DESDE UN MYSQL EXISTENTE AL MYSQL DE DOCKER
================================================================================

Si ya tiene una base de datos MySQL con datos que quiere pasar al
nuevo sistema con Docker, siga estos pasos:

PASO 7.1 - Exportar los datos de MySQL
----------------------------------------------------------------------
  a) Si tiene acceso a phpMyAdmin (panel web de MySQL):
     - Abra phpMyAdmin
     - Seleccione la base de datos
     - Haga clic en "Exportar"
     - Metodo: "Rapido" o "Quick"
     - Formato: SQL
     - Haga clic en "Continuar"
     - Se descargara un archivo .sql

  b) Si tiene acceso por linea de comandos:
     En CMD o PowerShell, ejecute:

         mysqldump -u usuario -p nombre_base_datos > backup.sql

     Le pedira la contrasena. Escribala y presione Enter.
     Se creara el archivo "backup.sql"

PASO 7.2 - Importar los datos en MySQL (Docker)
----------------------------------------------------------------------
  a) Copie el archivo .sql a la carpeta del proyecto Siif2

  b) En PowerShell, dentro de la carpeta Siif2, ejecute:

         docker compose exec -T db mysql -ularavel_user -p0690164 appserviciosinte_siif < backup.sql

     Explicacion:
       docker compose exec -T db  = ejecuta dentro del contenedor de BD
       mysql                      = el programa cliente de MySQL
       -ularavel_user             = el usuario
       -p0690164                  = la contrasena
       appserviciosinte_siif      = nombre de la base de datos
       < backup.sql               = "lee el archivo y lo importa"

  c) Espere a que termine. Puede tardar varios minutos si la base
     de datos es grande.

  d) Verifique en DBeaver que los datos se importaron correctamente.

PARTE 8: COMANDOS DE USO DIARIO
================================================================================

Estos son los comandos que usara con frecuencia. Todos se ejecutan
en PowerShell, dentro de la carpeta del proyecto Siif2.

  ATENCION: los comandos de esta parte son para DESARROLLO LOCAL.
  En un servidor de produccion los comandos son distintos (llevan
  "-f docker-compose.yml -f docker-compose.prod.yml"). Vea la PARTE 12.

  ENCENDER el sistema (cuando prenda la computadora):
  ---------------------------------------------------
         docker compose up -d

  APAGAR el sistema (cuando termine de trabajar):
  ---------------------------------------------------
         docker compose down

  REINICIAR todo el sistema:
  ---------------------------------------------------
         docker compose restart

  Ver si esta corriendo:
  ---------------------------------------------------
         docker compose ps

  Reconstruir todo desde cero (si algo se dano):
  ---------------------------------------------------
         docker compose down
         docker compose up --build -d

  Borrar TODO y empezar de cero (CUIDADO: borra la base de datos):
  ---------------------------------------------------
         docker compose down -v
         docker compose up --build -d

     La opcion -v borra los "volumenes" (donde se guardan los datos
     de la base de datos). Solo use esto si realmente quiere empezar
     de cero con la base de datos limpia.

PARTE 9: PROBLEMAS COMUNES Y SOLUCIONES
================================================================================

PROBLEMA: "Docker Desktop requiere WSL 2"
----------------------------------------------------------------------
  Solucion:
  a) Abra PowerShell COMO ADMINISTRADOR
     (clic derecho en PowerShell > "Ejecutar como administrador")
  b) Ejecute:
         wsl --install
  c) Reinicie la computadora
  d) Abra Docker Desktop otra vez

PROBLEMA: "puerto 3309 ya esta en uso"
----------------------------------------------------------------------
  Otro programa esta usando ese puerto.
  Solucion:
  a) Abra el archivo docker-compose.yml con el Bloc de Notas
  b) Busque la linea:    - "3309:3306"
  c) Cambie 3309 por otro numero, ejemplo:    - "3310:3306"
  d) Guarde el archivo
  e) Recuerde usar el nuevo puerto (3310) en DBeaver tambien
  f) Ejecute: docker compose up -d

PROBLEMA: "La pagina no carga en localhost:8080"
----------------------------------------------------------------------
  a) Verifique que los contenedores estan corriendo:
         docker compose ps
  b) Si algun contenedor dice "Restarting", vea los logs:
         docker compose logs app
         docker compose logs node
  c) Si ve errores de permisos, ejecute:
         docker compose down
         docker compose up --build -d

PROBLEMA: "Error de conexion a la base de datos"
----------------------------------------------------------------------
  a) Verifique que el contenedor de BD esta corriendo:
         docker compose ps
  b) Vea los logs de la base de datos:
         docker compose logs db
  c) Si la BD esta "healthy" pero Laravel no conecta, entre al
     contenedor y verifique:
         docker compose exec app php artisan tinker
     Luego escriba:
         DB::connection()->getPdo();
     Si conecta, vera informacion del PDO.
     Si no, vera un mensaje de error con detalles.

PROBLEMA: "Los cambios en el codigo no se reflejan"
----------------------------------------------------------------------
  a) Para cambios en archivos Vue/JS (frontend):
     Vite deberia recargar automaticamente. Si no lo hace:
         docker compose restart node

  b) Para cambios en archivos PHP (backend):
         docker compose exec app php artisan optimize:clear

PROBLEMA: DBeaver dice "Connection refused" o "Conexion rechazada"
----------------------------------------------------------------------
  a) Asegurese de que Docker esta corriendo
  b) Asegurese de que el puerto es 3309 (no 3306)
  c) Asegurese de que el host es "localhost" (no "127.0.0.1")
     Si localhost no funciona, intente con 127.0.0.1
  d) Ejecute en PowerShell:
         docker compose ps
     Y verifique que "laravel-db" dice "Up (healthy)"

PARTE 12: ARRANCAR EN LOCAL vs ARRANCAR EN PRODUCCION
================================================================================

El mismo proyecto sirve para las dos cosas, pero NO se necesita lo mismo en
cada ambiente:

  +---------------------------+------------------+---------------------+
  | Se necesita...            | Local (su PC)    | Produccion (VPS)    |
  +---------------------------+------------------+---------------------+
  | app (PHP/Laravel)         | SI               | SI                  |
  | nginx (servidor web)      | SI               | SI                  |
  | node (Vite en vivo)       | SI               | NO                  |
  | db (base de datos propia) | SI               | NO (usa la real)    |
  | Migraciones automaticas   | SI               | NO (a mano)         |
  +---------------------------+------------------+---------------------+

Por eso hay TRES archivos de Docker Compose:

  docker-compose.yml           = la base (app + nginx). Siempre se usa.
  docker-compose.override.yml  = SOLO local. Agrega node (Vite) y db.
  docker-compose.prod.yml      = SOLO produccion. Ajustes del servidor.

Lo importante de entender: Docker Compose carga el archivo "override"
AUTOMATICAMENTE cuando usted no pasa ningun "-f". Y en cuanto usted SI pasa
"-f", Compose deja de cargarlo. Eso es lo que hace la diferencia entre los
dos ambientes, sin tener que editar archivos a mano cada vez.


PASO 12.1 - Arrancar en LOCAL (desarrollo)
----------------------------------------------------------------------
  Es lo que ya venia haciendo, no cambia nada:

         docker compose up -d

  Esto levanta 4 contenedores: app, nginx, node (Vite con recarga en
  caliente) y db (la base de datos de prueba con el dump de ejemplo).

  Verificar:
         docker compose ps

  Abrir en el navegador:  http://localhost:8080


PASO 12.2 - Arrancar en PRODUCCION
----------------------------------------------------------------------
  a) PRIMERO compilar los assets (una sola vez por cada vez que cambie
     el codigo del frontend). En produccion no hay servidor de Vite, asi
     que el JavaScript/CSS tiene que quedar compilado en public/build/:

         docker compose -f docker-compose.yml -f docker-compose.prod.yml \
           --profile build run --rm assets

     Esto arranca un contenedor temporal, ejecuta "npm run build",
     y se borra solo al terminar (por eso el --rm).

     IMPORTANTE: revise que termine SIN el mensaje
     "[copy-sw] No se encontro ...". Si aparece ese mensaje, el build
     fallo y la pagina va a quedar en blanco.

  b) Levantar la aplicacion:

         docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d

     Esto levanta SOLO 2 contenedores: app y nginx. No levanta Vite ni
     crea ninguna base de datos: la app se conecta a la base de datos
     real que este configurada en el .env del servidor (vea la PARTE 13).

  c) Verificar:

         docker compose -f docker-compose.yml -f docker-compose.prod.yml ps

  CONSEJO: ese comando con los dos "-f" es largo y se repite mucho. Para
  no escribirlo cada vez, en el servidor puede definir una variable de
  entorno que le dice a Compose que archivos usar siempre:

         export COMPOSE_FILE=docker-compose.yml:docker-compose.prod.yml

  Con eso puesto, en ESA terminal ya puede usar los comandos cortos
  ("docker compose up -d", "docker compose ps", etc.) y Compose usara los
  archivos de produccion. Para que quede permanente, agregue esa linea al
  final del archivo ~/.bashrc del servidor.


PASO 12.3 - El archivo .env es distinto en cada ambiente
----------------------------------------------------------------------
  El archivo .env NUNCA se sube a git (esta en .gitignore porque tiene
  contrasenas). Eso significa que cada maquina tiene su propio .env:

    - En su PC: un .env con los datos de la base de datos de prueba
      (DB_HOST=db), APP_ENV=local, APP_DEBUG=true.

    - En la VPS: OTRO .env, que vive solo ahi, con los datos reales
      (DB_HOST=host.docker.internal), APP_ENV=production, APP_DEBUG=false.

  Los dos se llaman igual (.env) pero tienen contenido distinto, y como
  git no los toca, un "git pull" nunca pisa la configuracion de ninguno.

  VALORES OBLIGATORIOS EN PRODUCCION:

      APP_ENV=production
      APP_DEBUG=false          <-- CRITICO (vea la nota de abajo)
      LOG_LEVEL=error

  Por que APP_DEBUG=false es critico: con APP_DEBUG=true, cuando ocurre
  un error Laravel muestra en pantalla una pagina de diagnostico que
  incluye el codigo fuente, las consultas SQL y TODAS las variables del
  .env (contrasena de la base de datos, APP_KEY, etc.). En un servidor
  publico eso se lo esta mostrando a cualquiera que provoque un error.
  Con false, el visitante ve solo una pagina de error genérica y el
  detalle completo queda guardado en storage/logs/laravel.log.

  Despues de cambiar el .env hay que limpiar la cache de configuracion:

         docker compose -f docker-compose.yml -f docker-compose.prod.yml \
           exec app php artisan config:clear


PASO 12.4 - Migraciones en produccion (se corren a mano)
----------------------------------------------------------------------
  En local, el contenedor ejecuta "php artisan migrate" solo, en cada
  arranque. En produccion eso esta DESACTIVADO a proposito
  (RUN_MIGRATIONS=false en docker-compose.prod.yml).

  El motivo: la base de datos de produccion puede estar compartida con
  otra instalacion de la aplicacion que sigue en uso. Si el contenedor le
  cambia el esquema en cada reinicio, sin que nadie lo supervise, puede
  romper esa instalacion en vivo.

  Entonces en produccion se hace en dos pasos, con cuidado:

  a) PRIMERO ver que migraciones estan pendientes (esto NO modifica nada):

         docker compose -f docker-compose.yml -f docker-compose.prod.yml \
           exec app php artisan migrate:status

  b) Si esta seguro de que se deben aplicar, entonces si:

         docker compose -f docker-compose.yml -f docker-compose.prod.yml \
           exec app php artisan migrate --force

  RECOMENDACION: haga un respaldo de la base de datos antes del paso (b).


PASO 12.5 - Desplegar un cambio de codigo en produccion
----------------------------------------------------------------------
  La secuencia completa cada vez que sube cambios al servidor:

     1. Traer el codigo nuevo:
            git pull

     2. Recompilar los assets (si cambio algo de resources/js o css):
            docker compose -f docker-compose.yml -f docker-compose.prod.yml \
              --profile build run --rm assets

     3. Reiniciar la app:
            docker compose -f docker-compose.yml -f docker-compose.prod.yml \
              restart app

     4. Limpiar caches de Laravel:
            docker compose -f docker-compose.yml -f docker-compose.prod.yml \
              exec app php artisan optimize:clear

     5. Si hay migraciones nuevas, revisarlas y aplicarlas (PASO 12.4).

  EL PASO 2 NO ES OPCIONAL. Ni public/build/ ni public/sw.js estan en git (son
  artefactos de build): se generan en cada deploy. Si no se corre el build:

    - Falta public/build/manifest.json y Laravel muestra
      "Vite manifest not found at /var/www/public/build/manifest.json".
    - Falta public/sw.js, /sw.js da 404 y no hay modo offline (la app sigue
      funcionando normal online).

  Y ES IMPORTANTE QUE SE CORRA JUNTO CON EL CODIGO NUEVO: el service worker
  lleva adentro la lista de assets a precachear CON SU HASH
  (/build/assets/app-D8Qfp5CN.js, etc.). Un sw.js de un build viejo pide
  assets que ya no existen, recibe 404, el evento install falla y el service
  worker nunca se activa: el modo offline queda completamente muerto aunque
  todo lo demas funcione. Por eso sw.js dejo de estar versionado en git.

PARTE 13: CAMBIAR DE BASE DE DATOS (LOCAL <-> PRODUCCION)
================================================================================

Hay dos escenarios totalmente distintos y conviene tenerlos claros:

  ESCENARIO A - Base de datos LOCAL (la que crea Docker)
    Docker levanta un contenedor "db" con su propia base de datos, vacia,
    y le carga el dump de ejemplo que viene en el proyecto
    (docker-entrypoint-initdb.d/01_dump_patched.sql). Es una base
    independiente y desechable: sirve para desarrollar y probar sin
    riesgo. Los datos NO son los reales.

  ESCENARIO B - Base de datos de PRODUCCION (externa a Docker)
    La base de datos real ya existe en el servidor (por ejemplo el
    MySQL/MariaDB nativo de una VPS con cPanel), fuera de Docker. Aqui
    Docker NO crea ninguna base: la aplicacion se conecta a la que ya
    esta ahi, con sus datos reales.


PASO 13.1 - ESCENARIO A: usar la base de datos local
----------------------------------------------------------------------
  a) En el .env:

         DB_CONNECTION=mysql
         DB_HOST=db
         DB_PORT=3306
         DB_DATABASE=appserviciosinte_siif
         DB_USERNAME=laravel_user
         DB_PASSWORD=0690164

     El "db" de DB_HOST es el nombre del contenedor de base de datos
     dentro de la red de Docker. No es un dominio de internet.

  b) Levantar en modo local (asi se incluye el contenedor db):

         docker compose up -d


PASO 13.2 - ESCENARIO B: conectarse a la base de datos de produccion
----------------------------------------------------------------------
  Aqui hay DOS obstaculos que hay que resolver, y los dos son de red /
  permisos, no de la aplicacion:

  OBSTACULO 1: "localhost" no significa lo mismo dentro de un contenedor
  ------------------------------------------------------------------
  Dentro de un contenedor Docker, "localhost" y "127.0.0.1" apuntan al
  PROPIO contenedor, no al servidor. Si la base de datos corre en el
  sistema del servidor (fuera de Docker), poner DB_HOST=127.0.0.1 falla
  siempre con "Connection refused": el contenedor busca una base de datos
  dentro de si mismo, y ahi no hay ninguna.

  La solucion es el nombre especial "host.docker.internal", que si apunta
  de vuelta al servidor. Funciona porque docker-compose.yml ya incluye:

         extra_hosts:
           - "host.docker.internal:host-gateway"

  Entonces en el .env del servidor:

         DB_CONNECTION=mysql
         DB_HOST=host.docker.internal
         DB_PORT=3306
         DB_DATABASE=<la base de datos real>
         DB_USERNAME=<el usuario real>
         DB_PASSWORD=<la contrasena real>

  OBSTACULO 2: el usuario de MySQL solo acepta conexiones de "localhost"
  ------------------------------------------------------------------
  Los paneles tipo cPanel crean los usuarios de MySQL con permiso para
  conectarse UNICAMENTE desde localhost. Ahora la conexion llega desde la
  red interna de Docker (una IP tipo 172.18.0.x), asi que la base la
  rechaza con este error, aunque el usuario y la contrasena sean
  correctos:

         Host '172.18.0.4' is not allowed to connect to this server

  En MySQL/MariaDB un usuario es en realidad la combinacion
  usuario + host: 'usuario'@'localhost' y 'usuario'@'172.18.0.%' son dos
  permisos distintos aunque compartan el mismo nombre. (Por eso el panel
  de cPanel sigue mostrando un solo usuario: esa pantalla no muestra la
  parte del host.)

  Hay dos formas de resolverlo. Con CUALQUIERA de las dos alcanza:

    FORMA 1 (desde cPanel, recomendada):
      - Entrar a cPanel > "Remote MySQL" (o "MySQL remoto")
      - En "Add Access Host" agregar:   172.18.0.%
      - Guardar

    FORMA 2 (por linea de comandos, en el servidor, FUERA de Docker):

         mysql -u root -p

      Y luego, reemplazando usuario/clave/base por los reales:

         CREATE USER IF NOT EXISTS 'USUARIO'@'172.18.0.%'
             IDENTIFIED BY 'CONTRASENA';
         GRANT ALL PRIVILEGES ON BASE_DE_DATOS.*
             TO 'USUARIO'@'172.18.0.%';
         FLUSH PRIVILEGES;
         EXIT;

      Se usa el comodin 172.18.0.% (y no la IP exacta) porque la IP del
      contenedor puede cambiar cuando se reinicia.

      Esto NO toca el permiso que ya existe para 'USUARIO'@'localhost':
      agrega uno nuevo. La instalacion vieja que use localhost sigue
      funcionando igual.

      Para saber cual es el rango de IPs de su red de Docker:

         docker network inspect siif-2_laravel_network \
           --format '{{json .IPAM.Config}}'

  c) Levantar en modo produccion (asi NO se crea ninguna base local):

         docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d


PASO 13.3 - Verificar A QUE base de datos se conecto realmente
----------------------------------------------------------------------
  Esto es importante: la conexion puede decir "OK" y estar apuntando a la
  base equivocada. Para confirmarlo:

  a) Prueba rapida de conexion, que muestra el error real si falla
     (cambie los datos por los suyos):

         docker compose exec app php -r '
         try {
             $pdo = new PDO("mysql:host=host.docker.internal;port=3306;dbname=BASE",
                            "USUARIO", "CONTRASENA");
             echo "CONECTADO OK\n";
         } catch (PDOException $e) {
             echo "ERROR: " . $e->getMessage() . "\n";
         }
         '

     Como interpretar el resultado:
       "Connection refused"      -> problema de red (OBSTACULO 1)
       "Host ... not allowed"    -> problema de permisos (OBSTACULO 2)
       "Access denied for user"  -> usuario o contrasena incorrectos
       "Unknown database"        -> el nombre de la base esta mal
       "CONECTADO OK"            -> listo

  b) Ver la configuracion que tiene cargada la aplicacion:

         docker compose exec app env | grep DB_

  c) Resumen de la conexion segun Laravel:

         docker compose exec app php artisan db:show

  d) La comprobacion mas confiable (le pregunta al propio servidor de
     base de datos, no al archivo .env):

         docker compose exec app php artisan tinker

     Y adentro:

         DB::select('SELECT @@hostname AS host, DATABASE() AS bd, VERSION() AS version');

  e) Confirmar que los DATOS son los reales (no solo la estructura).
     Todavia dentro de tinker:

         Schema::getTableListing();              // listar tablas
         Schema::getColumnListing('t_personas'); // columnas de una tabla
         DB::table('t_personas')->count();       // cuantos registros hay

     Compare ese numero con lo que sabe que tiene la base real, o busque
     un registro que usted reconozca:

         DB::table('t_personas')
             ->where('nombre_completo_razon_social', 'like', '%NOMBRE%')
             ->get();

     Para salir de tinker:  exit

  CUIDADO cuando este conectado a la base de datos REAL: dentro de tinker
  use solo consultas de LECTURA (get, first, count). Evite ->save(),
  ->update(), ->delete() o factories, para no modificar datos de
  produccion por accidente.


PASO 13.4 - Volver de la base de produccion a la base local
----------------------------------------------------------------------
  Si cambio el .env para apuntar a produccion y ahora quiere volver a la
  base local, normalmente basta con restaurar los valores del PASO 13.1 y
  levantar en modo local otra vez.

  PERO puede aparecer este error:

         Container laravel-db  Error
         dependency failed to start: container laravel-db is unhealthy

  Y en los logs de la base de datos, un "Access denied for user".

  POR QUE PASA: la imagen de MySQL lee las variables MYSQL_DATABASE /
  MYSQL_USER / MYSQL_PASSWORD (que vienen del .env) UNICAMENTE la primera
  vez que arranca con el volumen de datos vacio. Despues de esa primera
  vez, ignora esas variables y usa lo que quedo guardado dentro del
  volumen "mysql_data". Entonces, si cambio usuario o contrasena en el
  .env, el healthcheck intenta entrar con los datos NUEVOS pero el
  servidor adentro tiene los VIEJOS, falla el login, el contenedor nunca
  llega a "healthy", y por lo tanto "app" nunca arranca y la pagina no
  carga.

  COMO CONFIRMARLO:

         docker compose logs db --tail=50

  (busque "Access denied for user" cerca del final)

  COMO ARREGLARLO: borrar el volumen para que la base se cree de nuevo,
  esta vez leyendo el .env actual.

  *** ANTES DE CONTINUAR: esto BORRA la base de datos local por completo.
      Es seguro solo porque esta base es la copia desechable de
      desarrollo. La base de datos de PRODUCCION no se toca: esa vive en
      el servidor, fuera de Docker, y no tiene ninguna relacion con este
      volumen. ***

         docker compose down
         docker volume ls | grep mysql_data
         docker volume rm siif-2_mysql_data
         docker compose up -d

  (ajuste "siif-2_mysql_data" al nombre exacto que le muestre el comando
   "docker volume ls". El prefijo depende del nombre de la carpeta del
   proyecto.)

  Al arrancar con el volumen borrado, el contenedor se inicializa desde
  cero: crea el usuario y la base con los valores del .env actual y vuelve
  a importar el dump de ejemplo. La primera vez tarda varios minutos
  porque el dump es grande.

PARTE 14: CERTIFICADO SSL (HTTPS) EN PRODUCCION - OBLIGATORIO
================================================================================

Esto NO es opcional ni cosmetico. Sobre HTTP plano el navegador DESACTIVA
tres funciones centrales de esta aplicacion, porque exigen lo que se llama
"contexto seguro" (HTTPS, o localhost):

  1. SERVICE WORKER = MODO OFFLINE. Sobre HTTP, navigator.serviceWorker no
     existe, el registro de resources/js/app.ts se saltea completo y no se
     instala ningun service worker. Sintoma tipico: dentro de Toma de Pedidos
     o Nuevo Reporte el modo offline parece funcionar (porque la app ya esta
     en memoria y IndexedDB si funciona sobre HTTP), pero al cambiar de una
     pantalla a la otra, o al entrar de nuevo, no carga nada.

  2. NOTIFICACIONES PUSH. Notification.requestPermission() y
     pushManager.subscribe() son de contexto seguro. Sobre HTTP el aviso de
     permiso nunca aparece, nadie se suscribe, y el envio siempre reporta
     "Push enviado a 0".

  3. GPS / GEOLOCALIZACION. navigator.geolocation esta bloqueado sobre HTTP.
     Ojo con el detalle: la llamada falla con "permiso denegado" AUNQUE el
     usuario haya aceptado el permiso.

  Ademas, sin HTTPS no se puede instalar la aplicacion en el telefono
  ("Agregar a pantalla de inicio"), que es el caso de uso de los RFV.

  No hay forma de arreglar esto por codigo: es una regla del navegador.


ARQUITECTURA
----------------------------------------------------------------------
  Lo que NO sirve (lo que el navegador marca como "Inseguro"):

      Usuario --> http://<IP>:8080 --> nginx de Docker --> app

  Lo correcto:

      Usuario --> https://appweb.gestoriasif.com   (puerto 443, con
                    |                               certificado)
                    v
              Apache de cPanel  (aqui vive el certificado)
                    |
                    v
              127.0.0.1:8080 --> nginx de Docker --> app

  El certificado va en el Apache de cPanel, no en el nginx de Docker. Motivo:
  Apache ya esta ocupando los puertos 80 y 443 del servidor para los otros
  dominios, asi que el contenedor no puede tomar el 443. Apache recibe la
  peticion cifrada y la reenvia sin cifrar por dentro del propio servidor
  (127.0.0.1), lo cual es seguro porque nunca sale a la red.


PASO 14.0 - URGENTE: cerrar la exposicion del codigo fuente
----------------------------------------------------------------------
  Si el subdominio muestra un listado "Index of /" con el proyecto, todo eso
  es descargable por cualquiera en internet: el codigo, el archivo .env con
  las credenciales de la base de datos, y el dump SQL con los datos.

  a) Borrar cualquier respaldo comprimido que este en la carpeta publica:

         rm -f /home/gestoriasif/public_html/appweb.gestoriasif.com/siif-2.zip

  b) Comprobar si el .env quedo expuesto. Abra en el navegador:

         http://appweb.gestoriasif.com/siif-2/.env

     Si el archivo se descarga o se muestra, esas credenciales se deben
     considerar comprometidas: cambie la contrasena de la base de datos en
     cPanel y actualicela en el .env.

  c) La configuracion de los pasos siguientes cierra esta exposicion, porque
     Apache va a dejar de servir esa carpeta y va a reenviar todo al
     contenedor.

  RECOMENDACION a futuro: el proyecto no deberia vivir dentro de public_html.
  Lo ideal es moverlo a algo como /home/gestoriasif/apps/siif-2, fuera de
  cualquier carpeta publica. Con el proxy configurado no hace falta que este
  en public_html para nada.


PASO 14.1 - Quitar la redireccion actual de cPanel
----------------------------------------------------------------------
  En la lista de Dominios de cPanel, appweb.gestoriasif.com aparece con
  "Redirige a: http://207.246.119.214:8080/". Esa redireccion es justamente
  la que manda al usuario a HTTP sin certificado, y hay que eliminarla:

    - cPanel > Dominios (o "Redirecciones", segun la version)
    - Buscar la redireccion de appweb.gestoriasif.com
    - Eliminarla

  Sin esto, el navegador va a seguir terminando en http://IP:8080 por mas
  certificado que instale.


PASO 14.2 - Emitir el certificado con AutoSSL (gratis)
----------------------------------------------------------------------
  Hagalo ANTES de configurar el proxy: la validacion del certificado necesita
  poder escribir y leer archivos en la carpeta publica del subdominio, y una
  vez que el proxy este activo esa carpeta ya no se sirve.

    a) cPanel > SSL/TLS Status  (o "Estado de SSL/TLS")
    b) Marcar appweb.gestoriasif.com
    c) Clic en "Run AutoSSL"  (Ejecutar AutoSSL)
    d) Esperar unos minutos y recargar. Debe quedar con un candado verde.

  AutoSSL usa Let's Encrypt: es gratuito y se renueva automaticamente.

  Si falla, casi siempre es DNS: el subdominio debe apuntar a la IP de esta
  VPS. Verifiquelo con:

         dig +short appweb.gestoriasif.com

  Debe devolver 207.246.119.214. Si devuelve otra cosa (o nada), primero hay
  que corregir el DNS y despues reintentar AutoSSL.


PASO 14.3 - Verificar que Apache pueda hacer de proxy
----------------------------------------------------------------------
  Como root en la VPS:

         httpd -M 2>/dev/null | grep -E "proxy_module|proxy_http_module|headers_module"

  Deben aparecer los tres:
         proxy_module (shared)
         proxy_http_module (shared)
         headers_module (shared)

  Si falta alguno, se activa desde:
    cPanel WHM > EasyApache 4 > Customize > Apache Modules
  y ahi se marcan mod_proxy, mod_proxy_http y mod_headers.


PASO 14.4 - Configurar el reverse proxy en Apache
----------------------------------------------------------------------
  IMPORTANTE: en un servidor con cPanel NO se edita httpd.conf directamente,
  porque cPanel lo regenera y se pierden los cambios. Hay que usar los
  archivos "include" de usuario, que cPanel respeta.

  a) Crear la carpeta del include para el vhost SSL (el de HTTPS):

         mkdir -p /etc/apache2/conf.d/userdata/ssl/2_4/gestoriasif/appweb.gestoriasif.com

  b) Crear el archivo de configuracion:

         nano /etc/apache2/conf.d/userdata/ssl/2_4/gestoriasif/appweb.gestoriasif.com/proxy.conf

  c) Pegar exactamente esto:

         ProxyPreserveHost On
         ProxyTimeout 300

         # Que Laravel sepa que el usuario entro por HTTPS. Sin esta linea
         # Laravel genera URLs http:// dentro de una pagina https:// y el
         # navegador las bloquea (contenido mixto) -> pagina en blanco.
         RequestHeader set X-Forwarded-Proto "https"

         # No reenviar la validacion de Let's Encrypt al contenedor, para que
         # la renovacion automatica del certificado siga funcionando.
         ProxyPass /.well-known !

         ProxyPass / http://127.0.0.1:8080/
         ProxyPassReverse / http://127.0.0.1:8080/

     Guardar con Ctrl+O, Enter, y salir con Ctrl+X.

  d) Aplicar los cambios (regenera los vhosts y reinicia Apache):

         /scripts/ensure_vhost_includes --user=gestoriasif
         /scripts/restartsrv_httpd

  NOTA: "gestoriasif" es el usuario de cPanel (se ve en la ruta /home/...).
  Si su usuario fuera otro, ajuste la ruta.


PASO 14.5 - Forzar HTTPS
----------------------------------------------------------------------
  Para que quien entre por http:// sea enviado automaticamente a https://:

    - cPanel > Dominios
    - En appweb.gestoriasif.com, activar el interruptor
      "Force HTTPS Redirect"

  (cPanel excluye /.well-known de esta redireccion, asi que no interfiere con
   la renovacion del certificado.)


PASO 14.6 - Cerrar el puerto 8080 al exterior
----------------------------------------------------------------------
  Esto es lo que hace que el HTTPS sea obligatorio y no una opcion: si el
  puerto 8080 sigue abierto a internet, cualquiera puede entrar por
  http://IP:8080, saltarse el certificado, y volver a quedarse sin modo
  offline, sin push y sin GPS.

  El proyecto ya lo resuelve: docker-compose.prod.yml publica el puerto solo
  en 127.0.0.1, de modo que unicamente el Apache del propio servidor puede
  alcanzarlo. Solo hay que levantar en modo produccion (PARTE 12):

         docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d

  Verificar que quedo escuchando solo en local:

         docker compose -f docker-compose.yml -f docker-compose.prod.yml ps

  En la columna de puertos debe decir 127.0.0.1:8080->80/tcp
  (y NO 0.0.0.0:8080->80/tcp).

  Comprobacion adicional, desde su PC (no desde la VPS): abrir
  http://207.246.119.214:8080 ya NO debe cargar nada. Eso es lo correcto.

  Si tiene firewall activo (csf o firewalld), aproveche para cerrar el 8080:

         # con csf: quitar 8080 de TCP_IN en /etc/csf/csf.conf y luego
         csf -r


PASO 14.7 - Ajustar Laravel para el HTTPS
----------------------------------------------------------------------
  a) En el .env del servidor, la URL debe ser la publica con https y SIN
     puerto:

         APP_URL=https://appweb.gestoriasif.com

  b) Limpiar la cache de configuracion para que tome el cambio:

         docker compose -f docker-compose.yml -f docker-compose.prod.yml \
           exec app php artisan config:clear

  c) Recompilar los assets, porque el service worker precachea URLs y hay que
     regenerarlo ya sobre el dominio definitivo:

         docker compose -f docker-compose.yml -f docker-compose.prod.yml \
           --profile build run --rm assets

  NOTA: el codigo ya incluye trustProxies (ver bootstrap/app.php), que es lo
  que hace que Laravel respete el X-Forwarded-Proto que envia Apache. No hay
  que configurar nada mas de ese lado.


PASO 14.8 - Verificar que todo quedo bien
----------------------------------------------------------------------
  a) Abrir https://appweb.gestoriasif.com  (sin puerto)
     - Debe aparecer el candado, y NO el aviso "Inseguro"
     - Debe cargar el login (no un "Index of /")

  b) Verificar que el service worker ahora SI existe. En el navegador,
     F12 > Console, escribir:

         navigator.serviceWorker

     - Sobre HTTP devolvia "undefined" (ese era el problema)
     - Sobre HTTPS debe devolver un objeto ServiceWorkerContainer

  c) F12 > Application (o Almacenamiento) > Service Workers: debe aparecer
     sw.js con estado "activated".

  d) Probar el modo offline de verdad:
     - Entrar a Toma de Pedidos con internet
     - F12 > Network > marcar "Offline"
     - Cambiar a Nuevo Reporte: AHORA si debe cargar
     - Guardar un pedido: debe quedar en la cola
     - Volver a poner internet: debe sincronizar solo

  e) Probar el aviso de notificaciones push: ahora debe aparecer el pedido de
     permiso (sobre HTTP nunca aparecia).

  f) Probar el GPS en Nuevo Reporte / Toma de Pedidos.


ALTERNATIVA MAS RAPIDA (si AutoSSL da problemas): Cloudflare
----------------------------------------------------------------------
  Si el DNS del dominio se puede mover a Cloudflare (plan gratuito), se
  obtiene HTTPS sin tocar Apache:

    1. Agregar gestoriasif.com a Cloudflare y cambiar los nameservers en el
       registrador del dominio.
    2. Crear un registro A: appweb -> 207.246.119.214, con la nube NARANJA
       (proxy activado).
    3. SSL/TLS > Overview > modo "Flexible" (o "Full" si luego instala el
       certificado en el servidor).

  Con eso el usuario entra por https:// y el service worker se habilita.
  Igual hay que hacer los pasos 14.0 (seguridad), 14.1 (quitar la
  redireccion) y 14.7 (APP_URL).

  Advertencia: en modo "Flexible" el tramo entre Cloudflare y su servidor
  viaja sin cifrar por internet. Es aceptable como solucion temporal, pero la
  opcion con AutoSSL + proxy de Apache es la correcta a largo plazo.
